Noema consumer case study

Un repo pequeño que sabe qué contexto necesita.

La prueba no es cuánta documentación podemos meter. La prueba es si distintos agentes pueden entrar, entender límites, trabajar y dejar evidencia sin releer todo el proyecto.

ContextoQualitySeguridadTrace
01 · Progressive context

Un entrypoint; contexto bajo demanda.

Todo agente inicia con `AGENTS.md`, el manifest y la tarea. Después sólo carga las fuentes requeridas por el modo actual.

Build

Construir / modificar

Carga spec del sitio + brand system. No necesita el plan de negocio ni toda la evidencia de auditoría.

Research

Investigar

Carga business plan + compliance. No necesita CSS, decisiones de layout o documentación de recovery.

Audit

Verificar

Carga quality gate + compliance. Evalúa límites sin asumir autoridad médica.

context: entrypoint: AGENTS.md default_mode: build modes: build: [SITE_SPEC, BRAND_SYSTEM] research: [BUSINESS_PLAN, COMPLIANCE] audit: [QUALITY_GATE, COMPLIANCE]
02 · Claims

Calidad como evidencia, no como adjetivo.

El manifest declara qué pretende garantizar el proyecto. Cada claim debe poder apuntar a una evidencia o gate.

Context efficiency

Entrada pequeña y modos explícitos. La regla es no leer más hasta que la tarea lo justifique.

Security boundaries

Sin backend, storage, cookies, tracking, red ni captura de datos en esta demo.

Visual coherence

Paleta, tipografía, motion y tono documentados para limitar deriva entre agentes.

Research groundedness

El plan separa patrones y supuestos de negocio; nunca presenta el escenario demo como forecast.

Delivery integrity

El artefacto público está aislado bajo `site/` y tiene workflow específico de Pages.

Contract conformance

El repo consume el workflow reusable de Noema pinneado a un commit inmutable.

Static gatelinks, privacy boundary, prohibited claims, assets and public pages.
Noema conformancemanifest, context, authority and protocol contract.
Pages deploymentvalidated static artifact deployed from `site/` only.
03 · Sensitive domain

Noema gobierna el proyecto; no suplanta al médico.

El manifest declara explícitamente lo que este repo no controla: consejo médico, decisiones clínicas, credenciales, datos de pacientes y verdad legal.

La demo tiene una frontera deliberadamente más estricta que una landing normal: ningún dato del formulario sale del navegador.
authority: owns: - static-site-code - demo-copy - visual-system - quality-evidence does_not_own: - medical-advice - clinical-decision-making - physician-credentials - patient-data - legal-compliance
04 · Trace

Lo que queremos aprender de este consumer.

Este greenfield permite comprobar si Noema sigue siendo útil cuando el proyecto no es grande. Si requiere demasiado protocolo para una landing, el diseño estaría fallando.

Entrar rápido

Un nuevo agente debe poder comenzar sin una lectura masiva del repo.

Trabajar dentro de límites

El contexto correcto debe aparecer por modo y la autoridad sensible debe quedar fuera del repo.

Verificar

Cambios tienen gates deterministas y revisión visual/humana donde corresponde.

Dejar aprendizaje

Los hallazgos útiles pueden regresar al ecosistema como evidencia para Noema/Skill Foundry sin convertir cada proyecto en un monolito documental.
